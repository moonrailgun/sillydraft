# 段落编号盲评修订（2026-11-07）

原逐字引文协议保留。V3 的 Gemini 两种排序各三次均无效，Astra 的两个有效排序达标，但原协议整体不完整。本修订在新请求前登记，不能修补旧输出后计分，也不把两套协议的分数混合。

## 唯一的评估变化

程序给完整正文的每个原有段落加上作品、章节和段落编号，例如 `A:C01P0001`。评委每维返回非空的 `sources` 编号数组，程序回填原文与章号。编号必须属于当前作品、存在且非空；同一维不得重复。仍须每本至少引用四章，并覆盖第 1–5、6–11、12–16 章。引用编号存在仅证明出处有效，不能证明解释或因果判断正确。

不改作者输入、正文、八维定义、量表、等权规则、模型、温度 0.2、20000 输出 token 上限，以及每位评委重点三维与总分差均 ≥ −0.3 的门槛。不额外提供已发现的缺陷或单书审计结论。保持严格 JSON、完整结束与错误校验，不自动修复响应。

## 运行与选择规则

1. 使用已生成的开发故事 `projection`，分别比较基线 SillyDraft / InkOS、V3 / InkOS；两位评委、两种排序，共八个初始请求。双方正文和编号算法相同，每个配对独立匿名。
2. 新目录使用 `judging-sources-baseline-projection` 和 `judging-sources-v3-projection`。冻结协议、脚本、依赖及正文哈希后才发请求，保留原始响应和所有失败。每个单元最多三次，只在诊断无效原因后显式补跑；有效单元不重抽样。
3. 使用现有汇总器。每位评委先对同一排序的全部有效尝试平均，再对两个排序等权；缺少任一单元仍不通过。原协议结果单独报告。
4. V3 开发集通过后，先冻结候选与验收记录，再解封 `bindery` 并按同一新协议比较候选和 InkOS。确认集不得用于选择本轮实现。开发集失败则先核验依据，再决定产品迭代。
5. 对关键指控检查原文前后文、可能的解释与运算；不人工改分。另报排序效应、评委分歧、单书审计漏检、篇幅和用量。本次重评无法证明统计显著提升，且不能消除长文本评委漏检。

## 实现与验证范围

复用现有 HTTP 捕获、解码、匿名映射和汇总，只给 `evaluate.judge` 增加新协议所需的提示与校验入口。新入口为 `evaluate_sources.py`，复用已有段落编号算法，不改生产写作代码或旧协议请求。测试覆盖全文保留、错书/未知/空白/重复编号、分数与跨章覆盖、旧协议请求不变，以及本地协议服务器下的双排序归属与无效响应保留。
